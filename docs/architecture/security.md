# 安全机制设计

## 1. 多层急停保障

| 层级 | 触发方式 | 响应时间 | 实现端 |
|------|---------|---------|--------|
| L1 硬件 | ESP32 限位开关 ISR 中断 | < 1ms | 嵌入式（暂未完成） |
| L2 嵌入式 | 超声波 < 10cm 自动刹车 | < 50ms | 嵌入式（暂未完成） |
| L3 App | 急停按钮 → BLE `{"c":"estop"}` | < 100ms | 手机 App |
| L4 上位机 | 远程急停 → Socket.IO → App → BLE | < 500ms | 上位机 + App |

急停原则：
- 急停帧绕过所有队列，最高优先级
- 任意端均可触发，无需等待确认
- 急停后进入 `ESTOP` 模式，必须管理员确认 + App 本地复位才能恢复

## 2. 通信断连保护

### 2.1 BLE 断连

- ESP32 检测 1.5 秒无心跳 → 全车急停，进入 Fail-safe
- App 检测 BLE 断开 → 上报 `BLE_LOST` 报警 → 上位机显示断连

### 2.2 Socket.IO 断连

- App 检测 3 秒无心跳 → 界面提示"上位机离线"
- App 仍可独立控制小车（手动遥控不依赖上位机）
- 上位机检测 App 断线 → 上报 `APP_OFFLINE` 报警
- Socket.IO 自动重连，重连后 App 重新上报 `app:hello`

### 2.3 双链路同时断

- 小车自动停止所有动作
- 等待任一链路恢复

## 3. 认证与权限

### 3.1 认证流程

```
App 打开 → 连接上位机 Socket.IO
  → emit app:auth {worker_id, password}
    → 上位机校验 bcrypt hash
      → 返回 pc:auth_result {ok, token, role}
        → App 保存 token，后续请求携带
```

### 3.2 角色权限

| 权限 | operator | admin |
|------|----------|-------|
| App 遥控小车 | ✅ | ✅ |
| 查看报警 | ✅ | ✅ |
| 创建工单 | ❌ | ✅ |
| 启动/暂停/取消工单 | ❌ | ✅ |
| 远程急停 | ❌ | ✅ |
| 管理员接管 | ❌ | ✅ |
| 人员管理 | ❌ | ✅ |
| 历史统计 | ❌ | ✅ |

### 3.3 JWT Token

- 生成：上位机认证通过后签发 JWT，有效期 24 小时
- 携带：Socket.IO 连接 auth 字段
- 刷新：App 重连时重新认证

## 4. 控制权仲裁

### 4.1 控制权状态

| 状态 | 说明 |
|------|------|
| `APP_MANUAL` | App 手动控制 |
| `PC_AUTO` | 上位机工单自动执行 |
| `PC_TAKEOVER` | 管理员接管 |
| `ESTOP` | 急停状态 |
| `FAULT` | 故障状态 |

### 4.2 切换规则

```
APP_MANUAL → PC_AUTO
  条件：App 空闲，收到上位机启动工单命令

PC_AUTO → APP_MANUAL
  条件：工单完成 / 工单取消 / 管理员释放

任何状态 → ESTOP
  条件：App 急停或上位机急停（最高优先级）

ESTOP → APP_MANUAL
  条件：管理员确认 + App 本地复位

任何状态 → FAULT
  条件：BLE 断开、命令超时、设备故障

FAULT → APP_MANUAL
  条件：故障排除 + 手动复位
```

### 4.3 CommandArbiter 判断逻辑

App 的 `CommandArbiter` 在每个命令执行前检查：

1. 当前控制权状态是否允许该命令？
2. 该命令是否需要抢占当前控制权？
3. 是否需要清空待执行命令队列？
4. 是否需要通知上位机控制权变更？

急停命令永远通过，不受控制权限制。

## 5. 数据安全

- 密码使用 bcrypt hash 存储，不存明文
- JWT secret 在上位机配置文件中，不硬编码
- SQLite 数据库文件权限限制为运行用户
- Socket.IO 未认证连接无法接收和发送业务事件
